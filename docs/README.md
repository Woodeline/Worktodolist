# 文档中心 · Worktodolist

项目所有说明类文档统一收在这里，**根目录只留代码、两个生态约定文件，以及给 AI 编码 Agent 的工具约定文件 `AGENTS.md`**（它必须放仓库根才能被编码工具自动发现，不属于说明文档）。

## 与根目录的分工

| 位置 | 放什么 | 为什么 |
|---|---|---|
| `README.md`（根） | 仓库门面：一句话定位、快速开始、构建方式 | GitHub 仓库页、`git clone` 后的第一眼，工具链默认读这里 |
| `CHANGELOG.md`（根） | 版本历史 | 版本入口，社区习惯在根目录 |
| `AGENTS.md`（根） | 给 AI 编码 Agent 的命令与红线 | 编码工具只在仓库根 / 就近目录自动发现，放 `docs/` 会失效 |
| `docs/`（本目录） | 其余全部说明文档 | 避免与代码文件混放 |

## 目录结构

```
docs/
├── README.md          本文档（索引 + 规范）
├── guide/             面向使用者的操作说明
├── design/            视觉 / 交互 / 结构设计
├── delivery/          阶段性交付与实施记录
└── plan/              方案与规划
```

## 命名规范

```
<YYYY-MM-DD>-<主题>.<ext>     有明确成文日期的过程稿 —— 日期前置，按时间排序
<主题>.<ext>                   长期有效的文档，不带日期
```

- **目录名用英文小写**（`guide` / `design` / `delivery` / `plan`）：目录名会被 URL、脚本、工具链反复处理，ASCII 最稳。
- **文件名用中文**：本项目文档面向中文读者，可读性优先于形式统一。
- **同内容的 md / html 双份渲染保持同名**，仅扩展名不同（如 `topydo-安装配置指南.md` 与 `.html`）。
- 文档间交叉引用一律走**相对路径**（同目录 `xxx.md`，跨目录 `../plan/xxx.md`），不写绝对路径。

## 新增文档怎么放

1. 判断归属：给人看的操作说明 → `guide/`；设计与视觉 → `design/`；一次任务的交付记录 → `delivery/`；方案与规划 → `plan/`。
2. 按上面的命名规范取名（有日期就日期前置）。
3. 在本文件的「文档索引」表里补一行 —— **索引不更新就等于没归档**。
4. 若文档由脚本生成，把脚本的输出路径指向对应目录（参考 `scripts/build_guide_html.py` 的 `__file__` 反推写法，不要写死绝对路径）。

## 归档口径：文档跟着版本走

**只有仍然描述当前实现的文档才留在 `docs/`。** 一个方案落地、被后续版本覆盖，或者只是一次性排查的过程稿，它的结论已经进了 `CHANGELOG.md` 和 `AGENTS.md` 的契约段，那份原稿就该删掉 —— 留着它，读者会读到与代码不符的规则，还会让索引维护变成负担。

- 设计 / 交付稿被新版覆盖时，**删稿，不写「已作废」的存根**：历史版本由 git 保留，需要溯源就 `git log -- <path>`。
- 只被某份被删文档引用的截图一并删除（`design/assets/<日期>/` 按批整目录清）。
- 保留判据：`AGENTS.md` 或 `README.md` 仍在引用它，或者它描述的东西今天还在跑。
- 已按此口径清理的批次记录在 `CHANGELOG.md` 的「文档清理」条目里，不在本文件重复列清单。
