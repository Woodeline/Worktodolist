## 1. 补上了一度以为「必须开窗口」才能拿到的分区尺寸

DOM 快照里侧栏/编辑器/辅助栏全缺（见 §3 的根因更正）。但截图已经在磁盘上，于是写了
`tools/png-measure.mjs`：零依赖 PNG 解码（IHDR/IDAT + zlib inflate + 5 种滤波还原）→
**逐列取众数色** → 找跳变点 → 输出分区边界。

校准过程值得记：单像素采样 + 阈值 30 在 `y=400` 切出 9 段，绝大多数是文字/图标抗锯齿造的假边界；
改成「列众数色 + 阈值 4」后得到 6 个切点 **44 / 338 / 342 / 858 / 862 / 1436**，
且 E30 / E34 / E37 / E38 / E39 **五帧位置完全一致**，全部对应真实 sash（4px）与窗口边框。

实测出来的工作台网格（1440×860，视口宽度可拖，不是常量）：

```
横向  活动栏 0→44 │ 侧栏 44→338 │ sash 338→342 │ 编辑器 342→858 │ sash 858→862 │ 辅助栏 862→1436 │ 边框 →1440
纵向  标题栏 0→40 │ 主体 40→836（E34 有终端时 编辑器 40→549 / sash 549→553 / 面板 553→836）│ 状态栏 840→860
```

SOLO 侧测到 `x=700` 纵向的 hairline 组（322/323、449/450、494、526/527、563/564、851/852），
E11 与 E40 两帧位置一致 → 行节奏 **32 / 36px**、卡片四周 **8px 画布留白**、截断处 44px **渐变遮罩带**。

## 2. 像素 ↔ 令牌对账：证明测距可信，也证明令牌值不够用

| 像素 | 令牌 | 结论 |
|---|---|---|
| 活动栏 `#222427` | `--vscode-activityBar-background #222427` | 一致 |
| 内容区 `#1a1b1d` | `--vscode-editor-background #1a1b1d` | 一致 |
| SOLO 画布 `#f5f5f5` | `--bg-bg-base-secondary #f5f5f5` | 一致 |
| 状态栏 `#2b2e31` | `--vscode-statusBar-background rgba(0,0,0,0)` | **不一致** → 状态栏有半透明叠加层 |
| 引导页动作胶囊 `#d1d3db` | `--vscode-button-background #d1d3db` | 一致（**跨 target 对账**） |

方法学结论：**令牌值不能预测最终像素**（叠加/混合），所以两套证据都得留；反过来若大面积冲突，
先怀疑测距参数（阈值/采样窗口），不是产品。

## 3. 两处对我自己前一轮记录的更正

1. **「DOM 预算偏小」是错的。** `cdp-capture.mjs` 默认 `--max-nodes 1400` 根本没用满（`visited` 只有 78）；
   真因是 **`--max-depth` 默认 9**，workbench 的 `.monaco-split-view2.horizontal` 在第 8 层，其子节点第 9 层起被裁。
   → §13 A1 的动作改为 `--max-depth 40 --max-nodes 6000`。**教训：采到「非空的浅树」比采到空树更危险**，
   它看起来像成功。读 `visited` 并和截图信息量对照是必做体检。
2. **notes/02 §2 的令牌分桶有误。** 我把 `--vscode-icon-icube-*` / `--vscode-icube*` 并进了「VS Code 血统」桶，
   得出「自研只有 101 条」。按名字前缀重新拆开后：

   | | 净 VS Code | `icon-icube`（codicon 字形） | `--vscode-icube*` | 裸名自研 | 合计自研占比 |
   |---|---|---|---|---|---|
   | 工作台 E30 | 2820 | 704 | 294 | 101 | 1099 / 3919 = **28%** |
   | SOLO E40 | 2791 | 702 | 294 | 601 | 1597 / 4388 = **36%** |

   → 原来那句「SOLO 自研令牌多 6 倍」只在裸名层成立；完整说法是：**AI 层在同一套体系上用了更多细粒度令牌，
   不是另建一套体系**。

## 4. 本轮最有价值的架构发现：令牌的双通道下发

```
--vscode-icube--bg-bg-base-secondary = #222427   (工作台镜像层)
--bg-bg-base-secondary               = #f5f5f5   (SOLO 裸名层)
```

- 工作台 `:root` 上有 **107 条 `--vscode-icube--<name>`** 形式的镜像；
- 其中 **94 条**同名裸名存在于 SOLO 层；
- 这 94 条里 **90 条取值不同** —— 因为两个窗口当时分别是暗/亮主题，**同一族令牌被按窗口各编译了一份**；
- 只在镜像层出现的 13 条是 `--cue-tr1`、`--cue-diff-add/remove`、`--solo-title-bar-*-scroll-shadow`、
  `--gradient-text-shimmer`、`--bg-bg-menu-tr0` —— 全是「只有工作台 CSS 需要、SOLO React 不需要」的条目，方向自洽。

判读：React/SOLO 层直接吃裸名；工作台层只能用 VS Code 变量管道，于是同一批令牌被冠上前缀灌进去。
**机制部分仍是推测**（未反查生成代码），取值部分是实测。→ §13 A9 已登记一个**离线可做**的验证动作：
在安装目录明文 JS 里检索 `--vscode-icube--` 的拼接点。

## 6. 收尾体检：每帧 DOM 到底被裁了没有（重要）

写完报告后做了一次全量审计（`visited` + 实际最大深度 + 落在第 9 层的节点数）：

| 帧 | visited | maxDepth | 停在第 9 层的节点 |
|---|---|---|---|
| E10 / E30 / E32 / E39 | 78 | **9** | 14 |
| E31 命令面板 | 110 | **9** | 22 |
| E27 信任对话框 | 103 | **9** | 23 |
| E33 / E34 / E35 / E37 / E38 | 69 | **9** | 13 |
| E11 / E40 SOLO | 58 | **9** | 10 |
| E00 引导欢迎 | 19 | 6 | 0 |
| E01 / E02 引导 | 15 | 5 | 0 |

三条结论：

1. **13 帧工作台/SOLO 全部触顶**，每帧有 10–23 个分支在第 9 层被砍 → §5.3 各视图「内部结构」目前
   只有截图目视级证据，尺寸是实测。这不是采集失败，是**参数太保守导致的静默降级**——树非空、有 box、有样式，
   看起来完全像采成功了。
2. **引导页 3 帧没被裁**（maxDepth 5–6）。所以「§7 最薄」的原因要改口径：不是取不到，
   是**引导页本身就是一棵 15–19 节点的浅树，且类名全哈希、没有结构锚点**。报告 §7 已按这个说法更正。
3. **A8 原登记为「离线可做」，验证后不成立**：`E35-settings.dom.json` 只有 69 个节点，是残壳，
   拆不出设置页内部结构 → 已并入 A1 的重采清单。剩下真正离线的只有 **A9**（明文 JS 反查令牌镜像生成点）
   和 **A11**（与 `src/index.css` 现有令牌对账，只读）。
