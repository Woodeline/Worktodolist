先划线

如果目标只是「更漂亮」，窗口外壳 + 文字 + 动效三项已经能拿到大部分收益；C 的代价主要花在重建输入法、文本编辑、无障碍和跨平台上。报告后文的「Tauri 外壳增强」就是这条低风险基线。

为什么不做「全量重写」

  • 真正贵的不是绘制，是边缘情况。重复任务以 due 为锚点推进、完成撤销连带下一次、备注的读·改·写、外部修改冲突、关闭窗口的刷盘握手、topydo 兼容、自动 Git 提交——这些都不是 C 代码能自动复用的资产。
  • UI 不是瓶颈，外壳才是。把窗口与绘制替换成原生，已经能拿到 80% 的视觉与体感收益；把对话页、工具页、Excel 导入导出一起重写，收益递减、风险陡增。
  • Rust 核心已经就位。现有 crate 同时产出 staticlib / cdylib / rlib，把 workspace / git / reminder 从 Tauri command 解耦后，就能直接接 C ABI；没必要为了 C 把数据层再写一遍。

这轮的正确姿势是换画布：设计语言、数据语义、快捷键、红线和测试口径全部保留；换掉的是窗口、绘制、输入和外壳整合。

路线选型：C 只是入口，框架才是分水岭

FRAMEWORK MATRIX / WINDOWS-FIRST

「用 C 写 UI」不是一个方案，而是一组取舍。下面的矩阵只回答一个问题：哪条路能在 Windows 上把「信号仪表」画得最准、又不会把输入法和无障碍一起赔进去。

IUP 这类「原生控件 + C」的路线体积小、上手快，但主题化能力不足，画不出「信号仪表」的窄发丝线与等宽节奏，故未列入主表。Dear ImGui 是 C++，不满足「C 语言」前提，同样排除。

为什么是 Win32 + Direct2D

  • 逐像素控制。1px 发丝线、2px 圆角、11px 等宽标签、左缘 2px 强调条——这些在 Web 里靠 CSS 近似，在 D2D 里就是精确的几何值；100% / 150% / 200% DPI 都按同一套逻辑绘制。
  • 窗口外壳是原生能力，不是画出来的。Mica Alt、DWM 圆角、暗色标题栏、Snap Layouts 悬停、系统菜单、贴靠与投影，都是 Win32/DWM 的一等公民；WebView 只能在外层套一个「像原生」的壳。
  • 没有运行时。Direct2D / DirectWrite / DWM 是 Windows 系统组件，exe 本体可以做到 2MB 以内；不需要 WebView2 常驻，启动与内存上限更可控。
  • 失败可回退。原生外壳与 Rust 核心之间是 C ABI；如果视觉或输入没过闸，保留 Rust 核心与数据层，回到 Tauri 只损失外壳工作量。

什么时候应该选 GTK4

如果「Windows 与 macOS 必须共用一套原生代码」是硬约束，GTK4 是唯一现实的 C 路线：它本身就是 C API，主题用 CSS，现有令牌可以几乎原样复用；GtkListView、输入法、无障碍都由框架承担。代价是 Windows 上要带数十 MB 的运行库，原生观感更接近「Linux 桌面应用」，Mica / Snap 这类 Windows 外壳能力拿不到。它不是「更差的 Win32」，而是另一种产品取舍。

为什么排除 LVGL / Nuklear

这两者是为嵌入式与游戏/工具界面设计的即时模式或轻量级 GUI：字库要预烘焙、输入法要自己接、文本编辑与无障碍几乎是空白。Worktodolist 是中文优先、键盘优先、长时间编辑的桌面应用，选它们等于把最难的 30% 留给项目自己。

C + WebView2 为什么不算答案

它能把外壳换成 C，但 UI 仍然是 HTML/CSS，视觉上限与现状一致；「C 原生美化」的卖点（DirectWrite、逐帧、自绘菜单）一个都拿不到。唯一价值是「去 Tauri 依赖」；如果目标是这个，可以做，但别把它包装成 UI 美化。

macOS 必须先裁决

项目现在同时出 Windows 与 macOS 包，而 Direct2D 是 Windows 独占。三条路：① Windows 用 C 原生、macOS 继续 Tauri（两套渲染，共享令牌与 Rust 核心）；② 两端都用 GTK4（一套代码，包体变大、Windows 原生感变弱）；③ Win32 + Metal/CoreText 双渲染器（多 4–6 人周）。

建议：不要让 macOS 阻塞 Windows 探针。先用 5 天验证 Win32 路线值不值得，再决定 macOS 是「并行维护」还是「另起 GTK4」。

C11 / WIN32 / DIRECT2D / RUST FFI

实现边界很清楚：C 负责窗口、布局、绘制、输入与外壳；Rust 继续负责 todo.txt 的语义与所有会写坏数据的逻辑。两者之间是一层薄薄的 C ABI，不共享内存布局，不跨 FFI 抛 panic。

为什么 Rust 核心能原样保留

  • 打包形态已经就位。现有 crate 的 crate-type 同时包含 staticlib 与 cdylib；把 workspace / git / reminder 从 Tauri command 里解耦成独立 core crate，就能生成 C 可链接的静态库。
  • 语义不搬家。完成/撤销、重复规则、备注、冲突、关闭握手、自动提交都留在 Rust 与现有测试里；C 侧只消费「当前列表」和「执行动作」两类调用。
  • 错误不跨越 FFI。Rust 侧 catch_unwind，所有失败变成 { code, message }；C 侧只处理错误码与 UTF-8 文案，不让 panic 穿过 ABI。
  • 线程模型简单。UI 线程持有 core 句柄；Git、备份、全量重载走 worker 线程，完成后 PostMessage 回 UI 线程。列表 JSON 在 1,000 条量级只有几十 KB，没必要为性能引入共享内存。

#[no_mangle]
pub extern "C" fn wl_toggle_complete(
    core: *mut Core, id: *const c_char, err: *mut WlError,
) -> i32 {
    match catch_unwind(|| { let c = unsafe { &mut *core }; c.toggle(cstr(id)?) }) {
        Ok(Ok(())) => 0,
        Ok(Err(e)) => write_error(err, e),
        Err(_)     => write_error(err, CoreError::Panic),
    }
}

风险与止损：哪些坑会让项目白做

RISK REGISTER / STOP-LOSS

C 原生项目的失败通常不是「画不出来」，而是低估了输入法、读屏、双轨维护和数据边界。下面这张表把每个风险拆成「早期信号 → 处置 → 止损线」，让项目在还能回头的时候回头。

止损线：什么时候必须停

  1. D5 探针：G1（IME）或 G4（UIA）任一不过，停止扩面，回 A 方案；不接受「再给两周试试」。
  2. P1 第 3 周末：完成 / 撤销、搜索、拖拽三条闭环仍未跑通，砍掉 P1 尾部（概览细化、状态栏动画），不延期。
  3. P1 结束：1,000 行滚动 p95 > 12ms，或崩溃率 > 0.1%，停在内部版，不对外发布。
  4. 任何时候：todo.txt 未改动行出现字节差异，回滚当日构建，先修数据再谈 UI。
  5. 双轨超过 4 周：仍未切换主线，冻结 C 版。两套 UI 同时演进，会把维护成本变成永久税。
沉没成本不是通行证

已经投入的周数不构成继续的理由。探针的结论、闸门的数字、用户的迁移意愿——三者任一为否，都应该停。停在一个可回退的 A 方案上，比硬撑一个半成品的 C 版更体面。

真正的成本也不只在写代码：设计评审、UIA 验收、三档 DPI 截图、签名证书、崩溃收集、支持文档、用户迁移沟通，这些都不会因为「原生」而消失。C 方案省下的是运行时开销，不是工程流程。

07

裁决：三条路，选一条，别骑墙

DECISION / PICK ONE

先把「美化」拆成两个问题：你要的是更好看，还是更像一个原生 Windows 程序？前者不需要重写，后者才需要 C。三条路都能交付，但不能同时走。

OPTION A · SHELL ONLY

Tauri 外壳增强

保留 WebView 与现有业务代码，只补窗口层：自绘标题栏、Mica / 暗色、系统菜单、字体与动效。先把「最像原生」的那一层拿到。

工期 1–2 人周 视觉增量 ≈ 60% 体积 / 内存 不变（WebView2） 平台 Windows · macOS 风险 低
OPTION B · NATIVE SHELL

C 原生外壳 + Rust 核心

Win32 + Direct2D / DirectWrite 重画外壳与列表；Rust 核心经 C ABI 原样保留；数据、备份、Git 行为不变。目标是把启动、滚动、内存拉到原生量级。

工期 10–16 人周（含探针） 视觉增量 100% 体积 / 内存 < 2MB / < 60MB 平台 Windows-first 风险 高（IME / UIA / 双轨）
OPTION C · POLISH

现有界面精修

不碰架构，只调排版、间距、对比度、动效与空状态。花小钱去掉最明显的「网页感」。

工期 0.5–1 人周 视觉增量 ≈ 20–30% 体积 / 内存 不变 平台 Windows · macOS 风险 极低

选择条件

如果……建议因为
Windows 占比 ≥ 80%，「轻、快、原生手感」是产品主张BC 方案是唯一能把启动、滚动、内存同时拉下来的路径；A 只能改外观。
近一年还要上 macOS / LinuxAB 首版只做 Windows；GTK4 分支会把 10 周变成 20 周。
本周就要让用户看到变化C精修可在一周内交付，且不引入迁移风险。
团队没有 Win32 / Direct2D 经验，也没有备份人选A先补人再谈 B；关键人风险不可接受。
工具 / 对话页重度依赖 Markdown、流式输出与 Web 组件B + 岛外壳原生，复杂页面用 WebView2 岛，避免把 AI 渲染也重写。
预算 ≤ 2 人周，或无法承受双轨维护A / CB 的工程成本主要在探针、UIA、双轨切换，不在画窗口。

如果选 B，先做这四件

  1. 原生 caption + Mica Alt + 暗色 + 圆角 + Snap 命中。窗口第一眼不再像网页，这是感知最强的 20%。
  2. DirectWrite 排版 + 4px 网格 + 42px 行。列表的「刻度感」来自字距、行高、对齐，而不是装饰。
  3. 虚拟列表 + 局部重绘 + 120Hz。滚动跟手是原生感的最大来源，也是最难伪装的一层。
  4. 完成 / 删除的 90 / 140ms 退场。让状态变化像仪表指针，而不是网页跳变。
这四件之外的功能可以慢

编辑浮窗、工具页、对话页都可以晚一个阶段；这四件不到位，C 方案就没有理由存在——用户不会因为「底层是 C」而觉得它原生，只会因为窗口、文字、滚动和动效像一个桌面软件。

开工前的八个问题

  • Windows 用户占比与 macOS 诉求是否已经量化？
  • 是否接受首版仅 Windows 原生？
  • 是否有至少 1 名 Win32 / D2D 工程师 + 1 名备份？
  • 是否能接受 10–16 人周，且期间 Web 版只维护不演进？
  • IME 探针是否已经排进第一周？
  • UIA / Narrator 验收是否写进里程碑？
  • 设计令牌是否已经机器可读（而非手抄）？
  • 数据字节级回归脚本是否已经存在？
八题里三题答不上来

就先做 A 方案。这不是保守，而是把「不知道」留在一个 1–2 人周的可回退范围里；C 方案的代价恰恰是把未知放到第 6 周才暴露。

本报告的建议

不是立刻重写，而是「一周探针 + A 方案兜底」。先花 1 人周做 D1–D5：窗口、列表、IME、UIA、基准；同时把 Tauri 外壳增强当作可回退的保底。D5 通过 → 进 P1；不通过 → A 方案已经在手，损失可控。这样「美化」从一场赌博变成一次可测量的采购。

D2D
Direct2D：GPU 加速的 2D 绘制 API，负责矩形、线条、位图与图层合成。

DirectWrite：文本布局与字形渲染，控制基线、字偶距、CJK 标点与行高。

Desktop Window Manager：负责窗口圆角、阴影、暗色标题栏与 Mica 材质。
Mica Alt
Windows 11 的窗口背景材质。模糊的是桌面壁纸，不是页面内容；只适合外壳。
UIA
UI Automation：Windows 的无障碍接口。自绘控件必须实现 provider，读屏才能读到。
IME

C ABI
C 调用约定。Rust 用 extern "C" 导出，C 侧按头文件调用，panic 不得跨越边界。
cbindgen
从 Rust 源码生成 C/C++ 头文件的工具，保证两侧签名一致。
ClearType
亚像素抗锯齿，需要不透明背景；在半透明材质上会产生彩边，应改用灰度抗锯齿。
Snap
Windows 11 的贴靠布局。最大化按钮悬停时出现，由系统接管，不是自绘浮层。
DPI
