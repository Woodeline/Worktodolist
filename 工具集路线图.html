工具集扩展路线图

基线 todolist-gui v0.1.5 现有工具 1 个（RTI） 运行时依赖 3 门禁 7 道 2026-10-07
结论

工具集现在是一个只有一格、没有内部骨架、与待办和对话都还没接线的抽屉。下一个迭代先不要加新工具，把抽屉做成柜子；之后按「工具碰什么资源」分批导入，新增成本才会从"改造外壳"降到一个组件 + 一条登记。

01

集成成本由「碰什么资源」决定，不由功能复杂度决定

→ 这张表就是导入顺序的依据
T1 · 纯计算

什么都不碰

成本
  • 单位换算 / 颜色空间
  • 正则测试 / 编解码
  • 日期差 / 进制 / 校验码
  • CSV · JSON 整形
新增设施：零
T2 · 本地文件

读文件，不写待办

成本
  • 日志过滤 / 文本 diff
  • 账单 · 台账解析
  • Markdown 预览
  • 批量重命名清单
需先有：选文件原语 + 权限记忆
T3 · 待办域

读且写 todo.txt

成本
  • 周报导出 / 统计
  • 批量优先级调整
  • 番茄跟踪
  • 重复任务生成
需先有：只读投影 + 确认落盘通道
T4 · 外部服务

出网

成本
  • 行情 / 天气 / 翻译
  • HTTP 调试
  • GitHub 查询
需先有：外联通道 + 分组开关
02

模块划分：三层 + 一条横切

能力与工具是一对多，所以 lib 按领域命名 
表现层  components/tools/
        ├─ <XxxTool>.jsx      只做布局与交互，状态自持
        └─ ToolShell.jsx     ← 待抽出的统一骨架

横切    components/tools/
        ├─ registry.js        只描述"是什么"
        └─ ToolsPage.jsx      只读 registry，不认识任何工具
────────────────────────────────────────────
适配层  lib/<domain>/
        ├─ files.js           导出 / 导入
        └─ lib/net/           ← 未来所有出网唯一出口

能力层  lib/<domain>/
        ├─ calc.js  stats.js  纯函数 · 无 DOM · 可单测
        └─ chart.js           画布绘制 + 令牌读取
01

算法必须在 lib/，否则不可测。现在 lib/rti/calc.js 能与 Python 基准逐项对拍，靠的就是这层解耦 —— 这是"能不能进门禁"的资格证书。

02

目录按领域命名，不叫 tools/。能力与工具是一对多：单位换算既服务工具页，也该被对话页调用（"3 海里等于多少公里"）。一绑到工具上就再也复用不了。

03

I/O 必须单一出口。文件走 files.js、网络走 lib/net/。工具自己 fetch 一次，就再也无法统一关停、统一审计。

03

registry 的演进：可扩展性的真实瓶颈

撑到第 5 个工具就会开始长特例

现 在（7 字段，够用）

idnamedesc detailtagsiconload
!
tags 只用于展示，不能筛不能分组；外壳读不到"这工具会不会写文件、会不会联网"。

建 议 补 齐（+6，全部声明式）

grouplayoutcapabilities keywordsstateVersionbeta
▲
registry 只描述"是什么"，绝不描述"怎么渲染"。一旦出现 render: () => … 这种字段，外壳就开始认识具体工具，现在的解耦白做。
04

三条接线通道：打通比加量更值钱

三处都已有半成品，补全成本很低
读

数据线 —— 抽 useTodoSnapshot() 只读投影。现在工具要读任务只能拖进整个 useTodoStore（列表页专用整块 hook），立刻产生耦合。

写

动作线 —— 复用 lib/actions.js 的 ACTIONS 表 + 已有的 ProposalModal：工具产出「建议」而不是直接改文件，走 建议 → 用户确认 → 落盘。通道已经存在，只是还没对工具开放 —— 投入产出比最高的一步。

记

事件线 —— eventLog.js 目前只记对话。工具的关键动作也进同一份 NDJSON（同一套按本地日历日归档），"我做过什么"才只有一条时间线。

05

设计方向：把工具集做成同一个产品的不同功能

而不是应用商店

三 种 版 式

inspector 左输入右结果，参数表 + 图表 + 导出
workbench 横向铺开：文件 + 大文本 + 结果表

补 可 视 化 令 牌

--ramp-1..5 顺序色阶（热力图、密度）
--div-1..5 发散色阶 · 涨红跌绿
i
现有 --chart-* 那 13 个是分类色，趋势与涨跌对比不够用。

危 险 度 可 见

不联网只读 会写入 todo.txt 会联网
i
由 capabilities 驱动，在标题旁标注 —— 让"数据主权优先"从口号变成看得见的事实。
06

优先级与大致顺序

顺序的关键是集成成本，不是业务紧急度
P0铺地基1 个迭代 · 不加工具
  1. 1ToolShell 骨架 + tool-* 样式规格 + 三种版式
  2. 2registry 补 6 个字段
  3. 3工具级 ErrorBoundary技术债 —— 现在一个工具抛异常会带走整个页面
  4. 4工具存储统一 toolStorage(id, version) + 迁移约定
  5. 5RTI 改造为骨架的第一个消费者（反向验证骨架成立）
  6. 6qa-tools 升级为外壳契约：新工具自动被检查（不写 todo.txt / 无裸色值 / 三档不漏 / 有崩溃隔离）
P1打通入口2–3 个迭代
  1. 7useTodoSnapshot() 只读投影
  2. 8工具产出 → ProposalModal 落盘通道
  3. 9对话页 → 工具路由（keywords + 动作 tool.open，复用 nlRules）
  4. 10工具动作写入 eventLog
  5. 11批量导入 4–6 个 T1 工具（零新设施，纯收益）
P2按业务需要2–4 个迭代
  1. 12T3 待办域工具（周报导出 / 批量优先级 / 统计）
  2. 13T2 本地文件工具 —— 前置：选文件原语 + 权限记忆 + 目录边界
  3. 14工具内搜索 / 最近使用 / 收藏
P3风险与远期条件成熟再说
  1. 15T4 联网工具 —— 前置三件套齐备才有资格做
  2. 16第三方脚本式工具注册 —— 安全边界成本远超收益，暂不建议
07

明确不建议做

引组件库 / 状态库

破坏 ≤5 运行时依赖的现状与既有门禁的判定口径。

云同步 / 分享 / 工具市场

单用户场景收益为零，且与"数据主权"叙事直接冲突。

每个工具自带导航或独立视觉

会退化成一堆迷你应用，失去"统一入口"这个唯一优势。

三级导航

工具多了用搜索 + 分组折叠解决，层级只会让人迷路。

08

需要拍板的四件事

拍完才动 P0 之外的东西
议题建议
01哪些工具允许写 todo.txt / done.txt？默认全部只读，白名单逐个开
02T2 的文件访问口径：每次现选，还是授权一个工作目录？授权工作目录 + 工具只能在其内活动（体验好，但必须立目录边界）
03新工具是否强制把算法放进 lib/ 且被 vitest 覆盖？强制 —— 这是"工具集"与"一堆页面"的分水岭
